# 歌词与歌曲身份

## 当前链路

1. 出声后 `TrackMetadataResolver` 请求自建 Worker `/v1/music/normalize`（版本 `music-metadata-v7-layered-identity`）。成功结果立刻写入 `Documents/track-metadata.json`，主键 `bvid+cid`。降级结果不落盘，界面继续显示原始标题。
2. 歌曲身份分层，不再把翻唱者塞进原唱：`canonicalTitle`、`originalArtists`、`coverPerformers`、`uploader`、`aliases`、`lyricSearchQueries`、`isCover`、`confidence`、`needsReview`。
3. 显示层尊重当前音源：翻唱为 `花譜（翻唱） · 原唱：土岐麻子`；官方曲保持 `アイドル` / `YOASOBI`。已识别身份覆盖正在播放、迷你播放器、锁屏、队列、首页/搜索/收藏、历史和缓存列表。
4. 歌词由 `LyricsResolver` 编排，不进入起播热路径：本地命中 → 私有 LDDC 聚合 → 现有曲库直连，并在每个来源内依次尝试高置信翻唱词与原唱。日语不只看假名：`You＆合図` 这种拉丁字母+汉字也会走 LRCLIB / VocaDB。LRCLIB 只用歌名搜，不把翻唱者塞进 artist_name。手动搜索仍聚合网易云 / QQ / 酷狗 / LRCLIB / VocaDB。不使用 B 站字幕。不恢复 LRCLIB 评分。
5. 版本范围与时间轴分开。自动匹配先对上这首歌/这个版本，同一档里再选逐字 > 逐行 LRC > 纯文本，不会为了有轴去用错版本。`exactCover` / `sameRecording` 可跟随播放；原唱套到翻唱上时，时长差 ≤3s 保留时间轴并提示「时间轴待确认」，更大差值降为纯文本。文本候选若歌名已过门且时长差 ≤25s，保留 LRC 并跟随播放（横幅「歌词 · 待确认」）；时长差过大才不跟随。用户手动点选、按翻唱/原唱搜索、或确认「适用于当前翻唱」时保留时间轴并跟随播放。
6. 首次写入默认偏移 0，避免把已经对上的官方词拧歪。后台只在本地音频互相关明显好过 0 轴时才改；结构打分只留给校准页「自动对齐」。滑过的偏移不会被后台改掉。变速翻唱对不上。
7. `LyricsStore` 仍使用 `Documents/lyrics-library.json`。成功歌词不过期；未命中缓存 7 天；「重新搜索」绕过失败缓存。

## LDDC 私有逐字歌词聚合

- 独立服务在 `services/lddc-lyrics-backend/`，以 GPL-3.0-only 进程调用固定到 commit `84631e8cd011fcc3f71ca0ae017e2c9758958ffc` 的 LDDC。Swift App 只调用受 Bearer 保护的 `bilimusic-lddc-lyrics-v1` HTTP 协议，不复制或链接 LDDC 代码。
- 服务并发查酷狗 KRC、QQ QRC 和网易云 YRC，先用标题、歌手和可选 ±4 秒时长门禁，再把行/字时间统一成毫秒。单请求总超时 18 秒，只缓存成功结果 24 小时，不记录 Bearer、Cookie 或歌词正文。
- App 校验协议版本、request ID、数量上限、行/字单调与边界，然后仍经过 `LyricsAutoMatchGate` 的歌曲身份与版本范围判断。已知翻唱在原唱 pass 中强制是 `canonicalOriginal`；不会因时长接近被误当为 `sameRecording`。
- 自动采用和手动搜索都遵守「先版本身份，再时间轴质量」：在同一版本范围内，已通过双重门禁的逐字词优先于逐行 LRC 和纯文本。手动列表显示「逐字」标识，同平台同 ID 去重也保留已验证的 timing hint 和文档；原唱逐字不得跨层压过当前翻唱版本。
- 私有服务未配置、不可达、超时、返回非逐字词或未通过 App 门禁时，继续旧的直连搜索；不会因错误候选饿死回退。自动采用继续要求服务端标题/歌手/时长门禁；手动搜索只放宽时长硬过滤，使加长视频、串烧或错误时长元数据仍能显示候选，但只有与当前曲目相差不超过 4 秒的逐字轴获得可靠优先，已知时长不符的条目明确标记后交给用户判断。2026-08-19 已部署到 Mac mini 的独立 `~/Library/Application Support/BiliMusic/LDDCLyricsBackend`，只绑定 Tailscale `100.108.23.60:8788`，Bearer 文件与用户级 LaunchAgent 均生效；Mac 构建机钥匙串仅保留同一 Token，构建时写入独立签名资源，避免最终 `Info.plist` 重建后丢失。误放到 Windows 的临时服务已停用，目录改名保留为可恢复备份。
- 手动候选的已验证文档按平台稳定 ID 缓存 64 份，不在下一次搜索开始时整体清空；搜索请求用 generation 隔离，旧请求不得覆盖新列表。用户选择带逐字提示的候选而临时文档缺失时，按候选标题、歌手和稳定 ID 向 LDDC 再取一次，禁止静默退回普通平台接口后报「没有找到可用歌词」。
- 真实收藏 20 首严格 PoC：当前 Swift 直连只有 2/20 首精确逐字，LDDC 达到 13/20，净新增 11 首；11 首翻唱中 7 首命中同版本，9 首官方/原唱中 6 首命中。4 首翻唱只找到原唱参考，3 首没有可信时间轴，均没有伪装为当前版本。精确命中的来源覆盖为酷狗 13、QQ 11、网易云 2。

## iPhone 本机逐字对齐（已停用的实验路径）

- **当前真相（2026-08-19 更正）**：播放器不再暴露本机生成/重新生成入口，设置页也不再允许下载模型，只保留已有模型的删除。真机两份 `bug_type 309` 报告均是 `SIGABRT`，发生在 `com.Metal.CompletionQueueDispatch` 的 `mlx::core::gpu::check_error`；一份经过 Forced Aligner，另一份经过 ASR。C++/Metal 完成回调直接 abort，Swift 无法捕获。以下内容只保留为实验历史与 smoke test 资产，除非 MLX/iOS 更新后重新做真机稳定性门禁，不得恢复为用户功能。

- `Qwen3-ForcedAligner-0.6B-4bit` 与 `Qwen3-ASR-0.6B-4bit` 通过 MLX 在 iPhone 本机运行。权重不打进 IPA，按需下载到 `Library/Application Support/LocalModels/` 并排除 iCloud 备份；设置页显示两者总占用并可一起删除。已有逐行轴也先用 ASR 检查整曲平移，再由 Forced Aligner 生成行内节奏；纯文本或强制重建则用 ASR 建完整粗轴。
- 该链路不进入播放、切歌、歌词获取或 Luna 演出热路径。用户主动触发后，当前音频若未缓存则先下载，随后用本地音频和现有逐行歌词生成时间轴；任务结束释放模型对象。
- 整首音频不能一次送入模型。真机曾以约 3.46 GB 常驻页触发 `per-process-limit` Jetsam；当前按已有逐行时间轴逐行切成带前后 0.25 秒上下文的窄窗口，并按文本节拍估算把明显包含间奏的超长 LRC 行窗口限制在 8 秒以内。模型内部每段清理 MLX cache；逐行调用比多行合并更慢，但避免相邻行和长静音拖动落点。
- 元数据首次清洗已经返回并缓存歌曲语言。模型语言采用混合判定：歌词里的假名/韩文是强证据；纯汉字才用清洗结果区分中文、粤语与无假名日语；拉丁歌词不会继承无关的中日韩标签。不得再硬编码英文。
- 中文、韩文按可见字符预分词，拉丁词组保持完整。日文先用系统 `NLTokenizer` 做外部词法分段，再按 MLX Forced Aligner 的规则拆汉字、保留假名词组；模型词组时间随后按汉字约 2 拍、普通假名 1 拍、小假名/促音/长音 0.5 拍映射回完整显示字符。所有模型结果仍与输入单元 1:1，显示层不丢字。
- 生成逐字轴前先用整曲 ASR 将歌词字符映射回音频；多行位移必须形成至少 60% 的稠密共识簇，且覆盖率、离散度与偏移范围同时过门，才整体平移原 LRC。重复副歌造成的后段错误配对作为离群值排除；不成簇、非线性漂移或模型失败均沿用原轴。校准后的可靠逐行 LRC 继续拥有行首决定权，Forced Aligner 在 ±2.5 秒宽窗口内只决定行内节奏；只有纯文本/ASR 完整重建的粗轴才允许模型重新选择行首。若一行出现大量 40ms、单词吞掉全句三分之一或单位节拍速度相差十倍，判为模型坍缩：保留该行首个可信落点，用上述日文节拍权重和最长 6.5 秒的人声区间重建该行；文档标记 `timingNeedsConfirmation=true`。重建后仍拥挤/跳跃才拒绝整首并保留原歌词。
- 纯文本或用户选择「忽略原时间轴重新生成」时，先由 Qwen3-ASR 将音频按 20 秒低峰值分块识别；本地只用单调 LCS 把识别字符映射回用户已有的正确歌词，要求字符覆盖、行覆盖和最少锚点同时过门。ASR 模型随后释放并清理 MLX cache，再加载 Forced Aligner 逐行精修，禁止两套模型同时驻留。门禁失败时不保存猜测时间轴。
- iPhone 17 Pro / iOS 27 长音频复测：189.177 秒、45 行、585 个字切成 23 段，585/585 一致；模型累计推理 6.234 秒，端到端 7.956 秒，MLX 报告峰值内存 1.430 GB。真实歌曲「サマータイムレコード」281 秒、64 行切成 19 段，573 个字符全部写回，推理 5.807 秒、峰值 1.552 GB；`lyrics-library.json` 已确认从 `line` 变成 `word`。模型约 985 MB，Debug App bundle 约 130 MB。

## Windows 离线高精度对齐

- 主机为 Ryzen 7 7700X / 32GB / RTX 5070 Ti 16GB。部署根为 `D:\BiliMusicAligner`，Qwen、音源分离和 WhisperX 分属三个虚拟环境，不复用或修改 ComfyUI Python。统一入口为 `scripts/windows_lyrics_aligner/run_offline.ps1`。
- 直接把伴奏混音交给 1.7B ASR 会出现长重复幻听；把整首精确歌词一次性交给 Forced Aligner 也会发生大量零时长与尾部坍缩，因此“大模型/全曲一次跑”不得作为高精度证据。当前固定先以 BS-RoFormer 分离 vocals，再以唯一歌词行的宽窗结果做 RANSAC 式位移共识，随后按相邻行中点划分时间所有权并逐行 BF16 对齐。
- WhisperX 3.8.6 日语 wav2vec2 CTC 是独立第二意见。两路行首差 ≤0.8s 才取中值；冲突则用稳定全局锚点，不擅自挑模型。最终逐字符节奏来自 WhisperX CTC，并以 50ms 最小相邻间隔和 180ms 末字下限做单调修复；完整显示文本、行顺序和不重叠是硬门禁。
- 「You＆合図」真机源音频的 Windows A/B 得到 +6.320s 全局位移（8/20 共识，MAD 0.040s），与 iPhone +6.241s 接近；26/40 行双模型共识，14 行回到全局锚点，8 行 Qwen 节奏失败被报告而非伪装成功。最终 40 行 / 364 字，最短 50ms、中位 180ms、无 ≤40ms；5 个 >1.5s 中最长 6.232s 对应显式 `Aa~` 长音。结果仅为离线产物，尚未接入 App 或替换手机缓存。

### App 高精度主机来源

- 上一段最后一句已过时：Windows 结果现已成为独立 `LyricsProvider.precisionHost`，但仍只由播放器菜单的显式操作触发。`PrecisionLyricsHostClient` 先以每个地址 5 秒的健康检查选择可达主机，默认先 Tailscale、失败后走家中局域网；两者均失败时明确返回，不允许 `waitsForConnectivity` 无限等待。随后创建确定性任务，主机缺音频时才上传当前本地缓存；App 取消轮询不会杀掉主机任务，稍后重复请求会直接取已完成缓存。连接、提交、上传和计算阶段在播放器持续显示。该路径不进入出声、切歌或自动歌词获取。
- Windows 服务位于 `D:\BiliMusicAligner`，通过 Tailscale 的 TCP 8765 提供认证 API。GPU 任务严格串行，登录后计划任务自启；Bearer 只存在 Windows token 文件和 Mac 钥匙串，仓库及文档不保存值。构建脚本把钥匙串值写入 App bundle 内独立、随 App 一起签名的 `BiliMusicPrecisionLyricsHost.plist`，客户端在 `Info.plist` 没有有效令牌时读取该资源；不能再直接改生成中的 `Info.plist`，因为 Xcode 会在脚本之后运行 `ProcessInfoPlistFile` 并覆盖修改。重复的 `bvid + cid + language + lyrics` 使用同一 job。主机 API 跳过不参与最终决策的整曲诊断 ASR，保留分离人声、Qwen 两遍局部定位、WhisperX 字符复核与最终共识，因此真实闭环由约 85–90s 降到 62.7s。
- 写回是双重门禁。主机先拒绝非单调或空 QRC；App 再要求逐行原文完全一致、行数一致、每行逐字单调、WhisperX 字符复核至少覆盖 50%、全局样本至少 6、MAD ≤1s、Qwen 节奏回退不超过 35%。WhisperX 覆盖 50–79% 可以写入但必须标记 `timingNeedsConfirmation`，80% 以上才视为确认；低于 50% 拒绝。任何网络、模型或门禁失败都保留原歌词与偏移。结果写回时偏移归零，因为校准已进入实际 QRC。
- 当前只接受已有逐行 LRC；本机 MLX 已停用，所以纯文本暂不提供生成入口。结构化并行声部暂不上传，避免单声道主机结果抹掉 `vocalLines`。设置页可覆盖主机 URL并测试健康状态；默认构建地址走用户自己的 Tailscale 主机。

- 第五首《メルト》证明两种假共识：第一遍有 23 个 onset 精确撞到 `source_start - 3s` 左边界；v2 又把受同一错误局部窗口约束的 Qwen/WhisperX 当作独立证据，主歌被提前 5–7 秒。整曲 exact-text Forced Aligner 与 1.7B ASR 诊断给出前段约 2.96、12.72、57.52、59.60、68.88 秒。v3 丢弃距窗口边界 ≤0.25s 的第一遍样本，以 8/10 内部样本得到 +0.560s / MAD 0.96s；局部双模型只有相互差 ≤0.8s、且距全局锚点 ≤1.25s 才能改行首，第一行放宽到 3s。pipeline 版本纳入 job ID，v3 完整重跑 76.995s：41/41 行、466 字、13 行受约束模型共识、28 行全局锚点、3 行节奏回退、41 行 WhisperX 字符复核；前段为 2.992、12.090、57.732、58.075、67.510 秒。
- `precisionHost` 文档已经把校准写进 QRC，所以持久化 offset 必须始终为 0，且不得启动 RMS offset refine。真机《メルト》的 `-10000ms / userSet=true` 不是用户手调：自动值在校准 sheet 未发生拖动时被 Slider 的结束回调重新标成用户值。Sheet 现必须先观察到 `editing=true`，才允许后续 `editing=false` 持久化；旧异常值由高精度缓存迁移归零。
- App 门禁必须区分原始时间轴行与显示声部行：物理 LRC 行数只和物理 QRC、主机 quality 行数比较；`LyricsParser` 排版后的源/结果行数另行比较。内联和声可把一条原始行拆成同一 `overlapGroup` 的两条同时显示行，这种相同行首合法；其他重复或倒退仍拒绝。错误必须带原词/QRC/主机或源/结果的具体计数。

## 同时演唱与多声部

- 歌词内部允许同一时刻存在多条声部，角色为 `lead / backing / duetA / duetB / together`，并用 `layerID + overlapGroup` 保留同组关系。旧 `LyricsDocument` 没有该字段时继续按原始歌词解析，持久化向后兼容。
- 首版只采用可解释的输入信号：`和声/伴唱/Backing/主唱/Lead/男/女/A/B/合唱` 前缀、行尾括号中的候选和声，以及完全相同时间戳的多行。普通尾部时间重叠不算二重唱，`间奏/前奏/伴奏/repeat` 等舞台说明不拆声部。
- 行尾括号拆出的主唱与和声共享逐行边界；相同时间戳的双行共享到下一个不同时间戳。纯文本经 ASR 建粗轴时，同一 `overlapGroup` 合并为同一个搜索窗口；Forced Aligner 随后对每个声部独立推理，允许逐字时间重叠。
- 生成的逐字结果除 QRC 外还保存结构化 `vocalLines`，防止扁平歌词格式再次丢失声部。完整歌词页同时高亮全部 active 声部；中央演出优先显示真实重叠组，Luna 不得用相邻行 composition 覆盖真实同时演唱。
- 这是保守的文本结构识别，不是音源分离。没有任何标记、只有混音音频时，目前不会凭空识别第二位歌手；真实歌曲上的括号误判率与双声部 Forced Aligner 精度仍需 iPhone 17 Pro 复测。

## 自建元数据清洗服务

- Cloudflare Worker：`https://bilimusic-metadata.mercari-email-sale-worker.workers.dev`
- 接口：`POST /v1/music/normalize`；健康检查：`GET /health`。
- 请求使用 Bearer 密钥；生产密钥只保存在 Cloudflare Worker Secret 和开发 Mac 系统钥匙串。
- 上游为私有 OpenAI 兼容 `gpt-5.6-luna`。服务端保护日文原名、拒绝把翻唱者/泛化 UP 当原唱，仅在高置信度时用曲库补原唱。
- KV 使用输入和 prompt 版本的 SHA-256 作为 key，缓存 30 天；`degraded` 结果不写 KV。

## UI

- 歌词是正在播放里的一种模式（`playerPage.lyrics`），不是独立 sheet 也不是新页；顶部 16:9 小封面返回封面，翻译/搜索收进 `⋯` 菜单，校准打开带 ±10 秒滑块的系统 sheet，可点「自动对齐」用歌词落点和本地音频对轴。手动搜索一次聚合网易云 / QQ / 酷狗 / LRCLIB / VocaDB，列表标明来源。进度/播放键/音量在歌词模式直接不出现；底部 `歌词 | AirPlay | 队列` 留在同一层，用来关闭歌词。封面缩放保持同一视图身份，只改 frame。
- 歌词页展示版本横幅：`翻唱版 · 精确同步`、`原唱歌词 · 时间轴待确认`、`纯文本歌词`、`歌词 · 不跟随播放`、`本地手动歌词`。
- 可重新识别歌曲、按翻唱/原唱搜索、导入纯文本或 LRC、手动修正身份，以及把当前歌词标为适用于翻唱版。

- 逐字行用 `LyricHighlightModel` 计算 sung/current/unsung；用户拖动歌词后 4 秒或点「回到当前句」恢复跟随。
- 完整歌词页不再把 `.current(progress)` 当成 `.sung`；每个真实字/词用左到右宽度 mask 按 progress 连续扫亮，扫描边缘仅有小幅羽化和当前字 glow。`LyricWordWrapLayout` 保留 token 原宽度与多行换行，可访问层仍输出完整句子。
